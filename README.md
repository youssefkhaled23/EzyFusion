# EzyFusion — property management and rent collection

A multi-organization rent-collection app: leases and invoice schedules, manual and online payments with allocation, manager approval workflow, a tenant portal, and a payment-gateway webhook. Built for the EzyFusion technical assessment.

## Stack

- Next.js 16 (App Router, Cache Components), TypeScript (strict), Tailwind CSS v4, shadcn/ui on Base UI (dark-only "Dark Premium" theme defined by CSS variables in `src/app/globals.css`)
- Supabase (local, Docker): PostgreSQL 17, Auth, Storage, Data API with Row Level Security
- Prisma 7 for server-side data access (connects as the database owner; see Security notes)
- Vitest for unit/DB/API tests, `playwright-core` + Chrome for browser tests

**The SQL migrations in `supabase/migrations/` are the only source of schema changes.** Prisma Migrate is never used; `prisma/schema.prisma` mirrors the database and `npm run db:check` verifies they agree.

## Setup (exact commands)

Prerequisites: Node.js 24, Docker Desktop running (at least ~8 GB memory allocated), free ports 54321-54324 and 3000.

```bash
npx supabase start
npx supabase db reset
npm install
cp .env.example .env.local
npm run seed
npm run build && npm start
```

Then open http://localhost:3000.

Notes:
- `.env.example` already contains working **local-only** values (the Supabase CLI's well-known development defaults). No edits are needed for a local run. Get the live values any time with `npx supabase status -o env`.
- The first `supabase start` downloads about 8 GB of Docker images.
- If `npx supabase` runs before `npm install`, npx downloads the CLI on the fly (latest version). `npm install` first uses the version pinned in `package-lock.json`; both work with the migrations here.
- `npm install` runs `prisma generate` (postinstall); no database is needed for that.
- `npm run seed` is idempotent. For a pristine state run `npx supabase db reset` first.

## Environment variables (`.env.example`)

| Variable | Purpose | Browser-safe? |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase API URL | yes |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Publishable key for browser/SSR clients (RLS protects every table) | yes |
| `SUPABASE_SECRET_KEY` | Bypasses RLS: seed, orphan-slip cleanup | **no, server only** |
| `DATABASE_URL` | Prisma runtime connection (database owner) | **no, server only** |
| `DIRECT_URL` | Direct connection for Prisma CLI commands | **no, server only** |
| `GATEWAY_X_SIGNATURE_KEY` | HMAC key for gateway webhook signatures | **no, server only** |
| `SEED_PASSWORD` | Password for every seeded account (seed script only) | no (never sent to the browser) |
| `WEBHOOK_URL` (optional) | Target of `gateway-sim.mjs` (default `http://localhost:3000/api/webhooks/gateway`) | n/a |

## Features

- **Billing rules** (`src/lib/billing.ts`): `generateSchedule`, `invoiceStatus`, `parseRinggitToSen` (integer sen, Malaysia time, month-end clamping, half-up proration).
- **Authentication:** email/password login, SSR session cookies, logout, role-aware navigation. Roles come from `memberships` and `tenants.user_id`, never from `user_metadata`. The API also accepts `Authorization: Bearer <token>`.
- **Staff / manager:** dashboard (overdue invoices, six-month collections), leases list, a manager-only create-lease form (`/leases/new`), and lease detail (invoices, payments, slip links), manual payment form (cash / bank transfer with slip upload), manager approve / reject / void.
- **Tenant:** own leases, invoices, payments, amount due now, "Pay now" (creates a gateway bill), return page, and phone-number update directly through the Data API (RLS + column grant).
- **Payments:** allocation by due date (deposit before rent, then period), payment cap (remaining balance minus pending), per-lease row lock for all money-changing operations, voiding.
- **Online payments:** `POST /api/leases/:id/gateway-bills`, signed webhook `POST /api/webhooks/gateway` (idempotent, concurrency-safe), `/payments/return` (read-only, never settles), simulator `node gateway-sim.mjs <bill_id> <amount_sen> [true|false]`.
- **Database:** RLS on every public table, tenant/staff/manager policies, append-only `audit_log`, private `payment-slips` bucket with organization-scoped Storage policies.

API: `POST /api/leases`, `GET /api/leases/options` (manager-only form choices), `GET /api/leases/:id`, `POST /api/leases/:id/payments`, `POST /api/leases/:id/gateway-bills`, `POST /api/payments/:id/approve|reject|void`, `GET /api/reports/collections?from=YYYY-MM&to=YYYY-MM`, `POST /api/webhooks/gateway`.

## Tests

The app and the Supabase stack must be running for the integration suites (`npm run build && npm start -- -p 3300`, `npx supabase start`, `npx supabase db reset`, `npm run seed`).

| Command | What it runs |
|---|---|
| `npm run lint` / `npm run typecheck` / `npm run build` | static checks and production build |
| `npm test` | unit tests (billing, allocation, signature, formatting) |
| `npm run test:tz` | the unit tests under `TZ=UTC`, `Asia/Kuala_Lumpur`, `America/New_York` |
| `npm run test:db` | schema, RLS, Storage and audit-log tests against the local database |
| `npm run test:api` | real HTTP tests incl. concurrency and the webhook (`API_BASE_URL`, default `http://localhost:3300`) |
| `npm run test:ui` | Chrome browser tests (`CHROME_PATH` to override `/Applications/Google Chrome.app/...`) |
| `npm run db:check` | Prisma schema vs. database consistency |

Integration tests create and clean up their own leases/payments, but audit-log rows cannot be deleted: run `npx supabase db reset && npm run seed` for a pristine database.

## Security notes

- Prisma connects as the database owner and **bypasses RLS**: every server query is authorized in code (`src/server/domain/access.ts`, `viewer.ts`).
- Browser bundles contain only the Supabase URL and publishable key (checked by `test:ui` and by scanning `.next/static`).
- `audit_log` is append-only via triggers; a superuser/table owner can still change the trigger through DDL.
- The per-lease lock is a convention: any new code that changes payments, allocations or bills must call `lockLease()` first.

## Known limitations

- Managers can create leases from the UI, but there is no UI to create tenants or units; no registration, password reset, or staff management.
- No rate limiting on login or the webhook; cookie-authenticated API calls do not refresh expired access tokens (page requests do, via `src/proxy.ts`).
- Money is displayed in MYR only; the dashboard has one bar chart (six-month collections, drawn without a chart library) and a table, with no filters or date-range controls.
- Unapplied online funds are never auto-applied later (voiding another payment does not reallocate them).
- Some tests depend on the current Malaysia date (they build leases around "today") and the browser tests need Google Chrome installed.
- Local development stack only: nothing is configured for deployment; Supabase analytics and the edge runtime are disabled in `supabase/config.toml` to save memory.
- `ai-logs/` holds the session transcript captured while the session was open; any further AI sessions used before submission must be exported there too.

## What would be implemented next

Tenant and unit management screens (leases can already be created from the UI), a live schedule preview in the lease form, account self-service (password reset), rate limiting and webhook replay protection, a database-level balance guard (trigger) as a second layer under the lease lock, charts and filters on the dashboard, automatic application of unapplied online funds under a defined policy, and CI running the full suite.
